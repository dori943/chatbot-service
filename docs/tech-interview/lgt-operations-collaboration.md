## O01. 리눅스 서버에서 이 프로젝트를 어떻게 실행하나요?

**모범 답변**

“Docker와 Compose를 사용할 수 있는 서버에 코드를 준비하고, `.env.example`의 변수 이름을 참고해 서버 환경을 설정합니다. 프로젝트 루트에서 `docker compose up --build -d --wait`로 백엔드와 MySQL을 시작합니다. 컨테이너 상태와 로그를 확인한 다음 웹에서 가입·로그인·질문을 검증하겠습니다.”

**꼬리질문: 어떤 환경에서도 소스만 복사하면 바로 실행되나요?**

“아닙니다. Docker 실행 환경, 사용할 포트, 환경 변수, DB 데이터와 스키마, AI API 접근이 필요합니다. 기존 데이터가 있으면 스키마 변경 적용도 별도로 확인해야 합니다.”

**근거:** [실행 문서](../../README.md), [Dockerfile](../../Dockerfile), [Compose](../../docker-compose.yml).

## O02. Dockerfile과 Docker Compose는 각각 무엇을 정의하나요?

**모범 답변**

“Dockerfile은 Python 3.12 기반 이미지에 의존성과 앱·화면 파일을 넣고 `python -m app.main`으로 실행하는 방법을 정의합니다. Compose는 백엔드와 MySQL 컨테이너, 네트워크, 환경 변수, 저장 볼륨을 함께 정의합니다. DB가 healthcheck를 통과한 뒤 백엔드를 시작하도록 연결되어 있습니다.”

**꼬리질문: `EXPOSE 8000`만 쓰면 외부에서 접속할 수 있나요?**

“포트를 문서화하는 선언만으로 호스트에 공개되지는 않습니다. 현재 Compose에는 `8000:8000` 매핑이 있고, 외부 접속에는 서버 방화벽과 네트워크 경로도 맞아야 합니다.”

**근거:** [Dockerfile](../../Dockerfile), [depends_on·ports](../../docker-compose.yml), [Uvicorn 실행](../../app/main.py).

## O03. API 키와 DB 비밀번호는 어떻게 관리하나요?

**모범 답변**

“실제 값은 코드에 넣지 않고 환경 변수로 전달합니다. 현재 앱 실행에서는 Compose의 `env_file`이 `.env`를 컨테이너에 주입하고, Python은 `getenv()`로 읽습니다. `.gitignore`로 실제 환경 파일을 제외하고, 공유용 `.env.example`에는 설정 항목을 안내합니다.”

**꼬리질문: 키를 한 번 Git에 올렸다가 삭제하면 해결되나요?**

“삭제 커밋만으로 이전 이력의 값이 사라지지는 않습니다. 노출된 키를 폐기·재발급하고 이력을 포함한 노출 범위를 확인해야 합니다. 현재 `.env`가 추적되지 않는다는 사실만으로 과거에도 노출이 없었다고 단정하지 않습니다.”

**근거:** [환경 변수 읽기](../../app/core/config.py), [DB 설정](../../app/db.py), [토큰 서명 키](../../app/utils/security.py), [.gitignore](../../.gitignore), [팀 민감정보 규칙](../../.github/CONTRIBUTING.md).

설정 이름 예: `AI_API_KEY`, `SECRET_KEY`, `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`. 모델·시간 제한·문맥 길이 등의 추가 이름은 코드와 [환경 변수 예시](../../.env.example)에서 확인합니다. 구술시험에서 실제 비밀 값을 보여줄 필요는 없습니다.

## O04. DB 호스트가 왜 localhost가 아니라 db인가요?

**모범 답변**

“백엔드와 DB는 서로 다른 컨테이너이므로 백엔드 컨테이너의 localhost는 백엔드 자신입니다. Compose의 같은 네트워크에서 DB 서비스 이름인 `db`로 접근하도록 설정했습니다. 그래서 컨테이너 밖에서 Python만 직접 실행할 때는 이 호스트 이름이 그대로 통하지 않을 수 있습니다.”

**꼬리질문: 일반 앱 DB 포트도 호스트에 공개되어 있나요?**

“현재 앱 Compose의 DB에는 호스트 포트 매핑이 없습니다. 별도 테스트 Compose는 로컬 `127.0.0.1:13307`을 테스트 DB에 연결합니다.”

**근거:** [DATABASE_URL](../../app/db.py), [앱 네트워크](../../docker-compose.yml), [테스트 DB 포트](../../docker-compose.test.yml).

## O05. 서버를 재시작하면 기록이 사라지나요? 스키마 변경은 어떻게 반영하나요?

**모범 답변**

“앱 DB 데이터는 `mysql-data` 볼륨에 저장하므로 컨테이너를 재시작하거나 다시 만드는 것과 데이터 삭제는 다릅니다. `init.sql`은 빈 데이터 디렉터리를 처음 초기화할 때 실행되므로, 파일을 바꾸고 앱만 재빌드해도 기존 테이블이 자동 변경되지는 않습니다. 데이터를 유지해야 한다면 백업 후 적절한 스키마 변경 절차를 준비해야 합니다.”

**꼬리질문: README의 `down --volumes`를 운영 데이터에 그대로 써도 되나요?**

“그 명령은 볼륨과 기존 계정·대화 데이터를 삭제하는 초기화 절차입니다. 데이터 보존이 필요한 환경의 마이그레이션 방법으로 사용하면 안 됩니다.”

**근거:** [볼륨 구성](../../docker-compose.yml), [테이블 생성](../../data/init.sql), [현재 README의 초기화 설명](../../README.md). 현재 코드에 별도 자동 마이그레이션 도구가 구현됐다고 주장하지 않습니다.

## O06. 외부 접속 가능이라는 평가 조건은 어떻게 증명하나요?

**모범 답변**

“평가자에게 실제 서비스 URL을 제공하고, 서버와 다른 외부 네트워크에서 접속해 가입·로그인·질문까지 확인하겠습니다. 로컬 `127.0.0.1:8000` 접속은 외부 접근의 증거가 아닙니다. 배포 주소, 검증 시각, 사용한 코드 버전과 성공 결과를 함께 기록하겠습니다.”

**꼬리질문: 현재 HTTPS와 리버스 프록시도 구현되어 있나요?**

“이 저장소의 Compose와 Dockerfile에서는 해당 구성을 확인할 수 없습니다. 운영 배포에서 HTTPS와 프록시를 구성한다면 실제 서버 설정을 따로 증빙해야 합니다.”

**근거:** [현재 Compose](../../docker-compose.yml), [기존 검증 범위](../testing-guide.md). 이 문답지 작성에서는 배포 URL이나 외부 접속을 검증하지 않았습니다.

## O07. 사용자가 오류를 신고하면 무엇부터 확인하나요?

**모범 답변**

“발생 시각과 동작, HTTP 상태코드, 응답의 `request_id`를 확인하겠습니다. 같은 ID로 서버의 요청 수신, AI 호출·성공 또는 실패, DB 저장 이벤트를 연결하고 저장된 행도 조회하겠습니다. 마지막으로 성공한 단계와 처음 실패한 단계를 구분해 인증·AI·DB 중 원인을 좁힙니다.”

**꼬리질문: 과제 예시의 `db_save_success`가 우리 코드의 로그 이름인가요?**

“우리 코드에서는 저장 성공을 `chat_saved`, 실패를 `chat_save_failed`로 기록합니다. 예시 문구와 같아야 하는 것이 아니라 요구한 이벤트가 확인되어야 합니다.”

**근거:** [LOG_EVENTS·RequestLoggingMiddleware](../../app/core/logging.py), [save_result](../../app/services/chat_db.py), [확인용 SQL](../../scripts/check_logs.sql). 테스트는 [test_chat_request_id_matches_logs_response_and_database](../../tests/test_logging.py).

현재 로그는 질문·답변 원문이나 토큰을 의도적으로 남기지 않고 오류 종류와 코드 위치 등을 기록합니다. 모든 로그 줄에 `user_id`가 포함된다고 말하지 말고, 저장된 기록의 사용자와 `request_id`를 연결해 설명하세요.

## O08. 자동 테스트를 어떤 층으로 나누었고 무엇을 증명하나요?

**모범 답변**

“AI 단위 테스트는 가짜 응답으로 문맥·분류·재시도 정책을 확인하고, API·DB 테스트는 별도 MySQL에서 인증·저장·조회·오류를 확인합니다. 브라우저 테스트는 화면에서 실제 API와 테스트 DB까지 연결하되 AI 응답은 대체합니다. 실제 AI 호출 테스트는 외부 연결과 응답을 확인하는 별도 선택 실행입니다.”

**꼬리질문: pytest가 성공으로 끝났으면 DB와 실제 AI도 검증된 것인가요?**

“아닙니다. 테스트 DB 설정이 없으면 DB 테스트가 건너뛰어질 수 있고, 브라우저와 실제 AI도 별도 실행 조건이 있습니다. 실행한 범위와 `skipped`, `deselected`를 확인해야 합니다.”

**근거:** [테스트 fixture](../../tests/conftest.py), [브라우저 테스트](../../tests/test_browser_integration.py), [실제 AI 테스트](../../tests/test_live_ai.py), [테스트 가이드](../testing-guide.md).

기존 문서에는 2026-09-28에 pytest 156개·JS 11개 등의 통과 기록이 있습니다. 이것은 기존 기록이며 이 문답지를 작성하면서 재실행한 결과가 아닙니다. 외부 배포 검증 결과와도 구분합니다.

## O09. 왜 개발 DB와 테스트 DB를 분리했나요?

**모범 답변**

“테스트는 같은 초기 상태에서 반복되어야 하고 사용자 데이터를 건드리면 안 되기 때문입니다. 현재 fixture는 매 테스트 전후에 대화와 사용자 테이블 데이터를 삭제하므로 전용 DB만 허용합니다. `MYSQL_TEST_URL`과 DB 이름 `chatbot_integration_test`를 확인하고, 별도 Compose의 MySQL을 사용합니다.”

**꼬리질문: 테스트를 여러 프로세스에서 동시에 돌리면 더 빠르지 않나요?**

“같은 테스트 DB에서는 서로 데이터를 지워 간섭할 수 있습니다. 현재 가이드도 같은 DB를 사용하는 병렬 실행을 금지하므로, 병렬화하려면 테스트별 DB 격리를 먼저 마련해야 합니다.”

**근거:** [database fixture·clear_database](../../tests/conftest.py), [전용 DB Compose](../../docker-compose.test.yml), [테스트 가이드](../testing-guide.md).

**준비할 증거:** 역할표, 개인 커밋·PR, 변경 파일·함수, 실제 테스트 또는 시연 기록. [팀 역할표](../../.github/CONTRIBUTING.md)만 보고 개인별 기여를 만들어 답하지 않습니다.

## O14. 시연 중 ‘로그인은 되는데 답변이 안 온다’면 어떻게 대응하나요?

**모범 답변**

“브라우저 Network에서 채팅 요청이 나갔는지와 응답 코드를 먼저 보겠습니다. 422는 본문 오류 코드에 따라 입력 형식과 AI 안전 차단을 구분하고, 401은 사용자 토큰, 503은 AI 설정·DB·인증 설정 문제를 확인합니다. `request_id`로 서버 로그를 확인해 AI 호출과 DB 저장 중 어디서 실패했는지 찾고, 원인에 맞게 설정이나 코드를 수정한 뒤 같은 경로를 재검증하겠습니다.”

**꼬리질문: DB에 실패 기록이 없으면 AI가 성공했다는 뜻인가요?**

“아닙니다. 인증·입력 검증에서 종료했거나, DB 자체 장애로 저장하지 못했거나, 요청 작업이 취소됐을 수도 있습니다. 브라우저와 서버 로그를 먼저 연결해야 합니다.”
