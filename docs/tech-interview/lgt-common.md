## C01. 이 프로젝트를 한 문장으로 소개하고 핵심 사용 과정을 설명해 보세요.

**모범 답변**

“로그인한 사용자가 웹에서 질문하면 서버가 AI API로 답변을 만들고, 질문·응답·처리 결과를 MySQL에 저장하는 챗봇 서비스입니다. 회원가입과 로그인 후 대화방에서 질문하고 같은 방에서 후속 질문을 이어갈 수 있습니다. 사용자는 본인의 전체 기록을 조회 API로 확인할 수 있습니다.”

**꼬리질문: 어떤 문제를 해결하고 누구를 위한 서비스인가요?**

“현재 구현은 웹에서 질문하고 이어서 대화하려는 로그인 사용자를 지원합니다. 특정 업무나 사용자 집단에 특화된 서비스라고 설명하려면 팀의 기획 근거와 사례를 추가해야 합니다.”

**근거:** [프로젝트 소개·API](../../README.md), [화면](../../templates/index.html), [채팅 라우터](../../app/routers/chat.py).

## C02. 질문 전송부터 답변 표시까지 순서대로 설명해 보세요.

**모범 답변**

“브라우저가 토큰과 방 ID·이름·질문을 `/api/chat`으로 보냅니다. 서버는 인증과 입력을 확인하고 같은 사용자·방의 성공 기록을 조회한 뒤 AI를 호출합니다. AI 결과를 검사하고 DB에 저장한 다음 성공 응답이나 오류를 반환하면, 브라우저가 같은 화면에 표시합니다.”

**꼬리질문: 과제에 적힌 ‘응답 반환 → 로그 저장’과 실제 코드의 순서가 같은가요?**

“실제 코드는 DB 저장 후 응답합니다. 저장이 실패하면 AI 답변이 있어도 성공 응답 대신 503을 반환합니다.”

**근거:** [requestReply](../../static/js/chat-api.js), [chat_main.chat](../../app/services/chat_main.py), [save_result](../../app/services/chat_db.py). [저장 실패 테스트](../../tests/test_validation_errors.py)의 `test_save_failure_returns_503_and_rolls_back`.

## C03. 프론트엔드, 백엔드, DB, AI API는 각각 무엇을 하나요?

**모범 답변**

“프론트엔드는 입력과 로그인 상태, 대화 화면, 오류 안내를 담당합니다. 백엔드는 인증과 검증, 문맥 조회, AI 호출, 저장을 연결합니다. DB는 사용자와 대화 기록을 보관하고, 외부 AI API는 전달받은 질문과 문맥으로 답변을 생성합니다.”

**꼬리질문: AI가 사용자 인증이나 DB 조회도 직접 하나요?**

“아닙니다. 인증과 DB 조회는 우리 서버가 수행하고, AI에는 서버가 구성한 문맥을 전달합니다.”

**근거:** [서버 진입점](../../app/main.py), [인증 의존성](../../app/core/dependencies.py), [AI 호출](../../app/services/AI_connect.py), [DB 작업](../../app/services/chat_db.py).

## C04. API란 무엇이고 우리 팀의 주요 API는 무엇인가요?

**모범 답변**

“API는 화면과 서버가 어떤 주소에 어떤 데이터를 보내고 받을지 정한 약속입니다. 우리 서비스는 회원가입 `/auth/register`, 로그인 `/auth/login`, 질문 `/api/chat`에 POST를 사용하고, 본인 기록 `/api/me/chats`에는 GET을 사용합니다. 채팅과 기록 조회는 Bearer 토큰이 필요합니다.”

**꼬리질문: 질문 요청 예시를 직접 말해 보세요.**

“본문은 `{"room_id":"room-1","room_name":"프로젝트 질문","question":"FastAPI가 뭐야?"}`이고, 헤더에 `Authorization: Bearer <토큰>`을 넣습니다. 사용자 ID는 본문에 받지 않고 검증한 토큰에서 가져옵니다.”

**근거:** [인증 라우터](../../app/routers/auth.py), [채팅 라우터](../../app/routers/chat.py), [ChatRequest](../../app/schemas/chat.py).

## C05. 로그인한 사용자만 질문하게 만든 이유와 방법은 무엇인가요?

**모범 답변**

“대화의 소유자를 식별하고 사용자별 기록과 문맥을 분리하기 위해서입니다. 화면에서도 비로그인 요청을 막지만, 실제 접근 제어는 서버의 `get_token_id()`가 수행합니다. 토큰 서명과 만료, 사용자 ID 형식, DB의 사용자 존재 여부를 확인한 뒤 채팅을 처리합니다.”

**꼬리질문: 개발자 도구로 로그인 화면을 우회하면 질문할 수 있나요?**

“화면 표시만 바꿔서는 서버 인증을 통과하지 못합니다. 유효한 토큰이 없는 직접 API 호출도 401로 거절합니다.”

**근거:** [get_token_id](../../app/core/dependencies.py), [인증 검증 테스트](../../tests/test_auth_dependency.py), [test_auth_required_before_ai](../../tests/test_chat_api.py).

## C06. AI는 이전 대화를 어떻게 기억하나요?

**모범 답변**

“우리 서버가 DB에서 같은 사용자·같은 방의 최근 성공 대화를 꺼내 매 호출에 다시 전달합니다. 기본값은 질문과 답변 한 쌍을 한 턴으로 본 최근 5턴이고, 길이가 크면 오래된 턴부터 더 제외합니다. AI가 우리 DB의 모든 대화를 자동으로 기억하는 구조는 아닙니다.”

**꼬리질문: 다른 사용자도 같은 room_id를 보내면 대화가 섞이나요?**

“조회 조건에 `user_id`도 함께 있으므로 다른 사용자의 기록은 포함하지 않습니다. 같은 사용자의 다른 방도 제외합니다.”

**근거:** [get_history](../../app/services/chat_db.py), [build_contents](../../app/services/AI_connect.py), [기본 설정](../../app/core/config.py), [방별 문맥 테스트](../../tests/test_chat_api.py).

## C07. 정상적인 질문과 잘못된 질문은 어떻게 구분하나요?

**모범 답변**

“Pydantic이 요청 필드와 타입을 확인하고, 서비스에서 앞뒤 공백을 제거한 뒤 내용과 길이를 검사합니다. 질문은 빈 값을 거절하고 기본 최대 5,000자이며, 설정값이 작으면 그 제한을 적용합니다. 방 ID는 1~64자, 방 이름은 1~100자이고 오류는 422로 반환합니다.”

**꼬리질문: 프론트에서도 검사하는데 서버 검사는 왜 필요한가요?**

“클라이언트를 거치지 않고 직접 요청할 수 있기 때문입니다. 화면 검사는 빠른 안내를 위해, 서버 검사는 실제 처리 기준을 지키기 위해 필요합니다.”

**근거:** [ChatRequest](../../app/schemas/chat.py), [validate_question·validate_room_id·validate_room_name](../../app/services/chat_main.py), [입력 경계 테스트](../../tests/test_validation_errors.py).

## C08. AI API가 실패하면 서비스 전체가 종료되나요?

**모범 답변**

“예상되는 AI 실패를 결과 객체와 오류 코드로 바꿔 요청 단위로 처리하도록 구현했습니다. 재시도나 대체 모델을 사용할 수 있는 오류는 정해진 정책으로 처리하고, 끝내 실패하면 실패 기록을 저장한 뒤 안내 응답을 반환합니다. 시간 초과는 504 `AI_TIMEOUT`처럼 원인을 구분합니다.”

**꼬리질문: 모든 장애 상황을 복구한다고 말할 수 있나요?**

“아닙니다. 코드가 처리하는 요청 예외와 서버 프로세스·네트워크·DB 자체의 장애는 구분해야 합니다. DB 저장마저 실패하면 실패 기록도 남기지 못할 수 있어 서버 로그를 함께 확인합니다.”

**근거:** [generate_answer](../../app/services/AI_connect.py), [chat_main.chat](../../app/services/chat_main.py), [오류 응답 처리](../../app/core/errors.py).

## C09. 이 서비스가 정상 동작한다고 어떻게 증명하겠어요?

**모범 답변**

“먼저 브라우저에서 가입·로그인하고 같은 방에 두 번 질문해 답변과 문맥을 확인하겠습니다. Network에서 요청 본문·상태코드·응답을 보고, `request_id`를 서버 로그와 DB 기록에 연결하겠습니다. 새 방과 다른 계정, 비로그인·입력 오류·AI 실패 사례도 비교해 정상 경로와 예외 경로를 구분하겠습니다.”

**꼬리질문: 화면에 답변이 보이면 저장까지 검증된 것인가요?**

“화면만으로는 부족합니다. 내 기록 API나 확인용 SQL로 실제 저장 내용과 사용자·방·시각을 확인해야 합니다.”

**근거:** [브라우저 통합 테스트](../../tests/test_browser_integration.py), [로그 연결 테스트](../../tests/test_logging.py), [SQL 확인 스크립트](../../scripts/check_logs.sql).

## C10. 현재 구현의 한계와 다음 개선을 하나씩 말해 보세요.

**모범 답변**

“현재 화면의 방 목록과 대화는 브라우저 저장소에서 관리하고, 서버 기록 조회 API로 화면을 복원하는 기능은 없습니다. 따라서 브라우저나 기기가 달라지면 같은 화면 기록을 자동으로 이어서 볼 수 없습니다. 개선한다면 서버의 방 관리와 기록 조회를 화면에 연결하고 페이지네이션을 추가하겠습니다.”

**꼬리질문: 그렇다면 현재 방별 문맥도 구현되지 않았나요?**

“방별 문맥은 이미 구현되어 있습니다. 방 ID·이름을 전송하고 DB에 저장하며, AI 문맥 조회는 사용자와 방으로 구분합니다. 서버 기록으로 화면을 복원하는 기능과는 다른 문제입니다.”

**근거:** [화면 상태 관리](../../static/js/chat.js), [현재 동작 범위](../../README.md), [방별 조회 조건](../../app/services/chat_db.py).
